# Протокол

Протокол программирования был обратно разработан авторами эталонных
инструментов; этот документ описывает, что реализует `rustsheng`. Байтовые
раскладки взяты дословно из `k5prog`, `k5prog-win` и `K5TOOL`.

## Кадрирование датаграмм

Каждое сообщение кадрируется как:

```
AB CD | len_lo len_hi | <payload> | crc_lo crc_hi | DC BA
```

- `len` — длина payload (little-endian, 16 бит).
- Только **payload и его 2 байта CRC** обфусцированы (XOR); заголовок,
  длина и завершитель передаются в открытом виде.
- CRC — **CRC-16/XMODEM** (полином `0x1021`, начальное значение `0x0000`) от
  открытого payload.

### Обфускация
XOR с повторяющимся 16-байтным ключом:
```
16 6c 14 e6 2e 91 0d 40 21 35 d5 40 13 03 e9 80
```
(Образы прошивки используют отдельный 128-байтный XOR-ключ — см. [прошивка](#firmware-images).)

### CRC на принимаемых датаграммах
Радиостанция использует CRC как обфускацию, а не для контроля целостности: ответы
содержат `0xFFFF` либо уже обфусцированное (ответы EEPROM), либо в открытом виде
(beacon режима прошивки). Поэтому `deframe` принимает датаграмму, когда **либо**
сырое (проводное) поле CRC, **либо** деобфусцированный CRC равны `0xFFFF`, либо
когда подлинный CRC совпадает — в соответствии с эталонными инструментами.

## Идентификатор сессии

Большинство команд повторяют 4-байтный идентификатор сессии / метку времени,
постоянный в течение сессии:
```
6a 39 57 64
```

## Команды (обычный режим)

Адреса — little-endian. `id` = первые два байта payload (little-endian).

| Команда | id | Payload |
|---------|----|---------|
| Hello | `0x0514` | `14 05 04 00 <session>` |
| Hello ack | `0x0515` | версия (16 байт) со смещения 4 |
| Чтение EEPROM | `0x051b` | `1b 05 08 00 addr_lo addr_hi len 00 <session>` (len ≤ 0x80) |
| Подтверждение чтения | `0x051c` | данные с байта 8 |
| Запись EEPROM | `0x051d` | `1d 05 <8+len> 00 addr_lo addr_hi len 01 <session> <data>` |
| Подтверждение записи | `0x051e` | повторяет адрес |
| Чтение RSSI | `0x0527` | `27 05 04 00 <session>` |
| Ответ RSSI | `0x0528` | rssi (9 бит) `[4..6] & 0x1ff`, шум `[6] & 0x7f`, glitch `[7]` |
| Чтение ADC | `0x0529` | `29 05 04 00 <session>` |
| Ответ ADC | `0x052a` | напряжение `[4..6]`, ток `[6..8]` |
| Сброс | `0x05dd` | `dd 05 00 00` |

RSSI вычисляется как `raw/2 − 160` дБм. ADC→вольты требует поканальной
калибровки радиостанции (`0x1f40`): `V = 7.6 × adc / calib[3]`.

## Геометрия EEPROM

| Константа | Значение |
|----------|-------|
| Размер | `0x2000` |
| Блок | `0x80` |
| Размер без калибровки | `0x1d00` |
| Область калибровки | `0x1e00..0x2000` (`0x200`) |
| Адресуемый диапазон (range ops) | `0x10000` |

Режимы записи:
- **Original** — заводской список/порядок блоков (из `uvk5.h`).
- **Most** — `0x0000..0x1d00`.
- **All** — весь `0x2000` (включая калибровку).

## Образы прошивки

`FirmwareImage::load` принимает оба формата:

- **Сырой (raw)** — распознаётся по сигнатуре таблицы векторов ARM
  (`data[2]=0x00, data[3]=0x20, data[6]=0x00, data[10]=0x00, data[14]=0x00`);
  используется как есть.
- **Vendor-упакованный** — завершается CRC и XOR-обфусцирован 128-байтным
  ключом прошивки. Проверяется CRC, расшифровывается, затем извлекается и
  удаляется 16-байтная строка версии по `0x2000`.

`pack()` — обратная операция: вставить версию по `0x2000`, XOR-обфусцировать,
добавить little-endian CRC. `rustsheng pack` выдаёт результат, **побайтово
идентичный** `K5TOOL -pack`. Ограничение размера flash: `0xf000` (выше
расположен бутлоадер).

Для образов прошивки действует жёсткий лимит по CPU: 0xf000 для V1 (DP32G030),
0x10000 для V2 (PY32F030) и 0x12000 для V3/K1 (PY32F071). Превышение —
ошибка. Это защищает бутлоадер от перезаписи.

## Прошивка (flash)

Прошивка управляется beacon-пакетом. Бутлоадер транслирует beacon; его
идентификатор выбирает протокол:

| | Beacon | Запрос версии | Запрос записи | Подтверждение записи |
|--|--------|-------------|-----------|-----------|
| **V2** (без шифрования) | `0x0518` | `0x0530` | `0x0519` | `0x051a` |
| **V5** (AES-CBC-128) | `0x057a` | `0x057d` | `0x057b` | `0x057c` |

Раскладка запроса записи (общая для обоих, payload 272 байта; V5 шифрует данные):
```
<cmd> 05 0c 01 | 8a 8d 9f 1d | chunk_no(LE16) chunk_count(LE16) len(LE16) 00 00 | <0x100 data>
```
- `cmd` = `0x19` (V2) или `0x7b` (V5); `id` = `0x1d9f8d8a` → байты `8a 8d 9f 1d`.
- `chunk_no = offset / 0x100`; данные — полная страница `0x100`, неиспользованный хвост заполнен `0xff`.
- Подтверждение записи: `chunk_no` в `[8..10]`, результат в `[10]` (0 = OK).

### Шифрование V5
V5 шифрует каждую страницу `0x100` алгоритмом **AES-128-CBC (без дополнения)**,
цепочкой через весь образ (один ключевой поток за сессию). Запрос версии
(`0x057d`) выбирает одну из 16 пар ключ/IV по `key_number`; каждый ключ и IV
разворачиваются по 32-битным словам перед использованием. Реализация AES
проверена тестовым вектором NIST SP800-38A.

Поток прошивки: `wait_for_beacon` → выбор протокола → отправка запроса версии →
для каждой страницы: собрать запрос записи, отправить, ожидать подтверждение
(игнорируя повторные beacon, до 5 попыток), проверить `chunk_no` и результат.
